Create a Durable Agent

A durable agent flips the authoring model of a durable workflow: instead of wiring steps together, you describe the goal in natural language and give the agent capabilities: activities, data events, and human tasks. The model plans the path at runtime, and because the agent runs as a durable workflow, every reasoning step, activity call, and wait survives crashes and restarts.

Why durable agents are different​

Standard AI agentDurable agent
A crash loses the conversation and in-flight tool callsEvery turn and activity call is recorded, so a restart resumes mid-plan
Waiting for external input holds a processWaits are suspended with zero resources, for days if needed
Retry logic lives in every toolEach activity has a declarative retry policy

Add a durable agent​

The steps below follow one example: a claimAgent that validates expense claims and pays them out.

  1. On the agentic integration's overview, select Add Agent.

  2. In the Add Agent dialog, under Create New, select Create Durable Agent.

  3. Fill in the Create Durable Agent form:

    FieldRequiredDescription
    NameYesThe name the agent is referenced by, for example claimAgent.
    ModelYesThe model provider the agent uses for its LLM calls. Defaults to Default WSO2 Model Provider. Select Create New Model Provider to use another one.
    RoleYesThe agent's primary function, for example Expense claim assistant.
    InstructionsYesWhat the agent should do. See Configure the agent.
    Input Data TypeNoThe structured payload a run starts with, for example an ExpenseClaim record. Leave it empty to start the agent with the query text alone.

  4. Select Create Agent.

The agent's canvas opens. It shows the durable agent with its role and instructions, the model provider it uses, and Add Trigger, Add Human Task, Add Data Event, and Add Tool/Activity for extending it.

Configure the agent​

To change the agent after you create it, select the menu (⋮) on the Durable Agent node, then select Edit. The Configure Agent panel holds the agent's role, its instructions, and its run limits. The model is the model provider node connected to the right of the agent.

FieldRequiredDescription
RoleYesThe agent's primary function. It appears under the agent's name on the node.
InstructionsYesWhat the agent should do, in natural language. The model plans from this text, so name the capabilities it should use and the outcome you expect.
Input TypeNoThe structured input a run is given, for example json or a record type.
Result TypeNoThe type a run produces, for example a record type. Left empty, the result is untyped.
Maximum IterationsNoThe most reasoning iterations the model may take in one turn. Defaults to 16.
Event TimeoutNoHow long the agent waits for each data event, as a duration such as {days: 1, hours: 2, minutes: 30}. Left empty, it waits indefinitely.
Maximum Event WaitsNoHow many data events a run may wait for before it fails. Defaults to 50.

Role and Instructions each take either a prompt or an expression. Keep the field on Prompt to write the text directly, or switch it to Expression to build the value in code, for example from a configurable.

Capabilities​

Activities​

An activity is a function marked as a workflow activity (@workflow:Activity). The model chooses which activity to call and when, and each call is recorded, so completed work is never lost or repeated across restarts. To create an activity from the agent canvas, see Build a Durable Agent.

You can also set an approval policy on a sensitive activity, so a person approves each call before the agent runs it. The approval requests appear on the Human Tasks page of the Integration Control Plane.

To register an activity with the agent:

  1. On the agent canvas, select Add Tool/Activity.

  2. Under Current Integration, select the activity you want the agent to have, payClaim here. Its register form opens.

  3. Choose the Approval Policy:

    • No Approval, the default, lets the agent call the activity directly.
    • Human Approval gates it. Before every call, the agent suspends durably and raises a review that carries the arguments it proposes. A reviewer proceeds with the call, optionally editing the arguments, or rejects it. Set Reviewer Roles to the roles permitted to decide, for example Finance, or name Reviewers instead. The same section also has Excluded Reviewers, Excluded Roles, Administrator Roles, Administrator Users, and the Title, Description, and Timeout of the review.
    • From Expression sets the policy in code.

  4. Choose the Retry Policy the engine applies when the activity fails:

    • No Retry, the default. The agent may still call the activity again.
    • Auto Retry retries with backoff.
    • Human Review asks a person to fix the failure.
    • Retry, then Review retries first, then asks a person.
    • From Expression sets the policy in code.

    For how each policy behaves, see Retry policies.

  5. Select Save.

The activity joins the agent node as a capability, drawn with a person badge while it is gated. Registering it is what makes it available to the model, so leave off any activity the agent never needs. To change the registration later, select the activity on the canvas. The form then also shows the Activity Name and the Activity Description.

No arguments to wire

Unlike a Call Activity step in a hand-wired durable workflow, the register form asks for no activity arguments. The agent maps them at runtime from what it has gathered. The model reads the activity's Activity Description, which defaults to the function's doc comment, so write the description and the parameter names clearly.

Data events​

A data event is a named channel that an external sender delivers a typed payload into. The agent suspends durably until the data arrives, just as a hand-wired durable workflow does with Await Data Events.

An event can also declare a response type: the value the agent returns to the sender after it has received and acted on that event. This makes the channel request-response. Leave the response type empty for a one-way channel that only delivers data.

To register a data event:

  1. On the agent canvas, select Add Data Event. The Register Data Event form opens.

  2. Fill in the form:

    FieldRequiredDescription
    Event NameYesThe channel name senders use. A channel named chat carries the conversation itself.
    Request TypeYesThe type of the payload sent to the agent on this channel. Defaults to string.
    Response TypeNoThe type of the agent's reply on this channel. Declaring one makes the channel request-response, read back with Get Data Event Result. Left empty, the channel is one-way.
    CardinalityNoHow the channel consumes its events. Multiple Events, the default, re-arms after every turn, so events can arrive repeatedly and from multiple senders. Single Event is consumed once per run.

  3. Select Save.

The event joins the canvas to the left of the agent, with its own Add Trigger for exposing the channel to senders. See Send an Agent Data Event.

Human tasks​

A human task is an escalation point the agent raises on its own judgment, for example when a claim looks unusual or its documents need a second pair of eyes. The task lands in the Integration Control Plane inbox of the roles you name, and the agent suspends durably until someone submits a decision, exactly like an Await Human Task step in a hand-wired durable workflow.

To register a human task:

  1. On the agent canvas, select Add Human Task. The Register HumanTask form opens.

  2. Fill in the form:

    FieldRequiredDescription
    Task NameYesIdentifies the task type, ReviewDocuments here. It is also the tool name advertised to the model, so name it for the decision it asks for.
    User RolesYes, unless users are namedThe roles permitted to complete this task, for example Finance. Only users holding a matching role see the task.
    TitleNoShort summary shown in the task inbox.
    DescriptionNoContext shown to the person completing the task, for example Check that the claim documents are legitimate.
    TimeoutNoMaximum time to wait for completion, as a duration such as {days: 1, hours: 2, minutes: 30}. On expiry, the agent is told the task timed out, so it can react. Leave it empty to wait indefinitely.
    Completion TypeNoThe type of the result the person submits, which drives the completion form in the task inbox. A plain approve or reject is a boolean, while anything richer is a record. Defaults to anydata, a free-form completion form. See Type the decision.

    Advanced Configurations holds Users, Excluded Users, Excluded Roles, Administrator Roles, Administrator Users, and Task Input Type, the shape of the input the agent supplies when it creates the task.

  3. Select Save.

The task joins the canvas to the left of the agent, under its task name. Task Name, User Roles, and Title each take either text or an expression, so any of them can be built in code, for example from a configurable.

No payload, no result variable

Unlike an Await Human Task step, the register form asks for neither a payload nor a result variable. The agent decides when to raise the task and what context to attach, and it reads the decision straight back into its reasoning. That's why Task Name and Description are what steer it.
